## 0. 결론 요약

| 질문 | 결론 |
| --- | --- |
| 기술적으로 가능한가? | **가능하다. 위험도 낮음.** pi 확장 API가 필요한 기능을 모두 제공하며, 이미 6개 이상의 구현체가 같은 방식으로 동작한다. |
| 이미 있는 플러그인인가? | **있다. 그리고 포화 상태에 가깝다.** 범용 "메신저 브리지"는 이미 6개 이상 존재한다. |
| 그럼에도 만들 가치가 있는가? | **있다. 단, 7번째 범용 브리지로는 안 된다.** 기존 구현들이 일관되게 비워둔 3개 지점(연속성 있는 핸드오프, 공유 가능한 작업 다이제스트, 전송 계층 무관 코어 + 어댑터 계약)에 집중하면 차별화가 가능하다. |
| 이 프로젝트의 정체성 제안 | **"핸드오프 브리지"** — 알림 봇이 아니라, 터미널 ↔ 메신저 사이에서 *같은 세션*을 잃지 않고 넘겨받는 도구. |

## 1. 요구사항 재해석

원문 요구:

> 현재 작업 내용을 discord, slack, telegram 등과 연결하여 **공유**하고 **다음 작업을 메신저에서 진행**할 수 있도록 해주는 원격 연결 플러그인

이 문장에는 서로 다른 두 기능이 들어 있고, 기존 도구들은 대개 앞쪽만 잘 한다.

| 요구 | 의미 | 기존 도구의 처리 |
| --- | --- | --- |
| **공유(share)** | "지금 무엇을 하고 있는지"를 사람이 읽을 수 있는 형태로 밖으로 보낸다 | 대부분 턴 단위 알림·`/status`만 제공. 구조화된 "작업 상태 카드"는 없음 |
| **다음 작업 진행(continue)** | 메신저에서 이어서 지시하고, 다시 터미널로 돌아와도 맥락이 유지된다 | 대부분 "메신저 → 세션 주입"까지. **터미널 복귀 시 맥락 병합**은 미해결 |

즉 이 프로젝트의 진짜 어려운 부분은 "메신저 연결"이 아니라 **세션 연속성**이다. 연결 자체는 이미commodity다.

## 2. 기술 타당성

### 2.1 pi 확장 API로 충분한가 — 충분하다

필요한 기능과 대응 API (실제 확인한 것만):

| 필요한 기능 | pi API | 확인 |
| --- | --- | --- |
| 수신 메시지를 에이전트 턴으로 주입 | `pi.sendUserMessage(text, { deliverAs })` | ✅ 문서 `extensions.md#pisendusermessagecontent-options` |
| 실행 중 턴에 끼어들기 / 대기열 | `deliverAs: "steer" \| "followUp"` | ✅ 동일 |
| 원격 명령 처리 | 코어에서 파싱, `ctx.abort()` / `pi.appendEntry()` | ✅ |
| 진행 상황 추적 | `tool_execution_start/update/end`, `turn_end`, `agent_settled` | ✅ |
| 완료 시점 판정 | `agent_settled` (재시도·자동 압축까지 끝난 시점) | ✅ `agent_end`는 부적합 |
| 대기 중 UI 안내 | `ctx.ui.notify/setStatus` | ✅ |
| 세션 정체성·이름 | `pi.getSessionName()`, `ctx.sessionManager` | ✅ |
| 설정 파일 경로 규약 | `CONFIG_DIR_NAME` | ✅ |
| npm/git 배포 | `package.json`의 `pi` 매니페스트 + `pi install` | ✅ `packages.md` |

### 2.2 실제 제약 (설계에 반영해야 하는 것)

1. **전송 폴링은 프로세스당 1개만 가능**
   Telegram `getUpdates`, Discord gateway, Slack Socket Mode 모두 동일 봇 토큰으로 동시 연결하면 충돌한다.
   → **단일 인스턴스 락**이 필요하다. 기존 구현들(`pi-messenger-bridge`, `PiRelay`)도 모두 이 문제를 락 파일로 해결한다.
   → 서브에이전트가 세션을 스폰할 때 중복 폴링이 발생하므로 락은 필수다.

2. **확장 팩토리에서 백그라운드 리소스를 시작하면 안 된다**
   pi 문서가 명시한다: 소켓·타이머·워처는 `session_start` 이후로 미뤄야 하고, `session_shutdown`에서 멱등하게 정리해야 한다.
   → 브리지 생성/시작 시점을 `session_start`로 고정해야 한다.

3. **전송별로 제약이 다르다**

   | 전송 | 메시지 상한 | 마크다운 | 스레드 |
| --- | --- | --- | --- |
   | Telegram | 4096 (사실상 바이트 기준) | HTML | 없음 |
   | Discord | 2000 (chars) | markdown | 있음 |
   | Slack | ~4000 (chars) | mrkdwn | 있음 |

   → 청킹과 마크다운 변환은 **전송별 능력(capability)에 따라** 코어에서 수행해야 한다. (현재 `src/core/chunk.ts`, `src/core/markdown.ts`로 구현·테스트 완료)

4. **다중 세션 × 단일 봇 토큰** 문제
   여러 pi 세션을 한 봇으로 제어하려면 로컬 브로커(별도 프로세스)나 "1세션 = 1봇" 바인딩이 필요하다.
   → v1은 **세션당 1봇/1전송**으로 단순화하고, 브로커는 v2로 미룬다. (PiRelay가 브로커를 쓰는 이유가 여기 있다)

5. **보안은 편의가 아니라 요구사항이다**
   구조적으로 원격 코드 실행 채널이다. 봇 토큰이 유출되면 곧 셸이다.
   → **페어링 코드를 같은 채팅으로 보내면 안 된다.** 코드는 로컬 터미널에만 표시하고 사용자가 채팅에 입력해야 한다.
   → 송신 본문은 반드시 리댁션을 거친다. 프롬프트/툴 인자는 로그에 남기지 않는다.
   (이 두 가지는 현재 코어에 테스트로 고정되어 있다 — `src/bridge.test.ts`)

6. **메신저는 신뢰 경계 밖이다**
   E2E 암호화 없음, 플랫폼 보안 모델에 의존. 문서에 명시해야 한다.

### 2.3 위험도 평가

| 위험 | 영향 | 완화 |
| --- | --- | --- |
| 경쟁 포화 | 높음 | 차별축 3개에 집중, "안 하는 것"을 명시 |
| 플랫폼 3개 유지보수 비용 | 높음 | 어댑터 계약 + conformance 테스트로 격리, v1은 Telegram 단독 |
| 자격증명 설정 마찰 | 중간 | 단일 토큰 Telegram 우선, 나머지는 후순위 |
| 보안 사고 (토큰 유출=셸) | 높음 | 터미널 전용 페어링, 리댁션, allowUsers 사전 신뢰, 채널은 명시적 호출만 |
| pi API 변경 | 중간 | 코어는 pi를 import하지 않음. 어댑터(`src/index.ts`)에만 의존 격리 |
| 서브에이전트 중복 폴링 | 중간 | 단일 인스턴스 락 + 문서화된 제약 |

**판정: 기술 타당성 통과. 남은 리스크는 제품/유지보수 리스크이지 기술 리스크가 아니다.**

### 3.3 결론: 비어 있는 3개의 칸

경쟁 매트릭스에서 **모든 프로젝트가 ○인 열은 정확히 3개**다.

1. **터미널 복귀 시 맥락 병합** — `slack-bridge`가 tmux로 세션을 *전환*하지만, 그것은 "터미널을 뺏는" 방식이다. 로컬 TUI를 살려둔 채 원격 턴을 세션에 병합하고 돌아왔을 때 이어지는 동작은 아무도 하지 않는다. `pi-gateway`는 애초에 채팅별로 세션을 *분리*해서 이 문제를 회피한다.
2. **공유용 작업 다이제스트** — 모두 "턴이 끝났다"는 알림과 `/status` 한 줄은 보낸다. 브랜치·diff 통계·TODO·테스트 결과·마지막 요청을 묶은 **읽을 수 있는 상태 카드**를 만들어 채널에 공유하는 기능은 없다.
3. **어댑터 계약 / 외부 전송 확장** — 6개 모두 전송 로직이 내부에 하드코딩되어 있고, 재사용 가능한 계약이나 conformance 키트를 공개하지 않는다. 새 메신저를 붙이려면 포크해야 한다.

## 4. 차별점 제안

### 제안 A — "핸드오프 브리지" (연속성 우선) ★ 추천

**한 문장**: 메신저에서 이어서 작업하고, 터미널로 돌아오면 그 작업이 이미 세션에 반영되어 있다.

구체 동작:
- 로컬 TUI는 계속 살아 있다. 원격 프롬프트는 **같은 라이브 세션**에 주입된다(steer/followUp).
- 원격에서 시작한 턴은 세션에 남아, 터미널 복귀 시 별도 동기화 없이 그대로 보인다.
- 세션을 죽이거나 tmux로 뺏지 않는다. 이것이 `slack-bridge`와의 결정적 차이.
- `/connect handoff`로 "지금부터 이 채팅이 이 세션의 입력면"임을 명시적으로 선언/해제.

근거: 요구사항의 "다음 작업을 메신저에서 진행"이 정확히 이것이며, 매트릭스에서 유일하게 모두 비어 있다.

### 제안 B — 작업 다이제스트(공유 카드)

**한 문장**: "지금 어디까지 했는지"를 한 장으로 만들어 채널에 공유한다.

- 포함: 세션명, cwd/브랜치, 미완 TODO(n/m), 변경 파일 요약(+/-), 테스트 결과, 마지막 요청, 한 줄 요약.
- 길이 예산 초과 시 우선순위 낮은 섹션부터 자동 생략(테스트로 고정됨 — `src/core/digest.test.ts`).
- 발행 경로: `/connect digest`(로컬), 원격 `digest`, (v2) 턴 종료 시 자동.
- 팀 채널에 붙이면 그대로 스탠드업 리포트가 된다. 기존 도구에 없는 산출물.

근거: 요구사항의 "현재 작업 내용을 공유"를 알림이 아니라 **산출물**로 해석한 것.

### 제안 C — 전송 무관 코어 + 어댑터 계약 (확장성)

**한 문장**: 새 메신저를 붙이는 일이 "어댑터 1개 + conformance 테스트 통과"로 끝난다.

- 코어는 pi도 네트워크도 모른다. `Transport` 인터페이스만 안다.
- `FakeTransport`로 크레덴셜 없이 전 구간을 테스트한다.
- 전송 어댑터가 지켜야 할 계약을 테스트로 강제한다.
- 부수 효과: Matrix·Zulip·Teams·SMS·이메일 등 커뮤니티 어댑터가 가능해진다.

근거: 6개 프로젝트 모두 이 계층이 없다. 우리가 TDD를 택했기 때문에 자연스럽게 얻어지는 구조이기도 하다.

### 제안 D — 런타임 봇 SDK 제로 (보안/감사 친화)

- `discord.js`/`grammy`/`@slack/bolt` 없이 HTTPS + 폴링/Socket Mode 최소 구현.
- 의존성 최소 → 감사 범위 최소, 공급망 리스크 최소.
- 트레이드오프: 플랫폼별 프로토콜을 직접 다뤄야 함(구현 비용 증가). v1 Telegram에는 합리적, Slack Socket Mode는 판단 필요.

근거: PiRelay는 7개 런타임 의존성(discord.js, grammy, gifuct-js, pngjs, qrcode-terminal, proper-lockfile, jiti)을 갖는다. 보안 민감 사용자에게는 실질적 차이.

### 제안 E — 크레덴셜 없는 개발/리플레이 (개발자 경험)

- `FakeTransport` + 엔벨로프 record/replay로 봇 토큰 없이 브리지 동작을 재현·회귀 테스트.
- 기존 프로젝트의 문서는 수동 스모크 테스트 중심이다.
- 이는 우리의 TDD 철학과 정확히 일치하며, 동시에 제품 기능(어댑터 개발 도구)이 된다.

### 추천 조합

> **A(핸드오프) + B(다이제스트) + C(어댑터 계약)을 정체성으로, D를 제약으로, E를 방법론으로.**

즉:

| | 내용 |
| --- | --- |
| **정체성** | 알림 봇이 아니라 **핸드오프 브리지**. 세션을 뺏지 않고 넘겨받는다. |
| **차별 기능** | 작업 다이제스트 공유 카드 |
| **구조적 차별** | 전송 무관 코어 + 어댑터 계약 + conformance 테스트 |
| **제약** | 런타임 봇 SDK 제로, 최소 의존성 |
| **방법론** | 테스트 우선, 크레덴셜 없이 전 구간 검증 |

## 5. 의도적으로 하지 않는 것 (범위 규율)

기존 도구와 정면 충돌하지 않기 위해 v1에서 명시적으로 제외한다.

| 하지 않음 | 이유 / 대안 |

| RBAC·툴 정책 엔진 | `pi-gateway`가 이미 잘한다. 우리는 승인 게이트 1종만 |
| pi TUI 전체 미러(`/fork`, `/tree`, 모델 전환 UI) | `pi-telegram-plus`가 이미 잘한다 |
| 서버 상주/Docker 에이전트 호스팅 | `pi-remote-agent`의 영역. 우리는 로컬 우선 |
| 다중 세션 브로커(별도 프로세스) | v2. v1은 세션당 1전송 |
| WhatsApp/Matrix/Twitch | v2 이후. Telegram → Discord → Slack 순서 |
| E2E 암호화 | 플랫폼 한계. 문서에 명시 |

## 6. MVP 범위 제안

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| **v0 (완료)** | 전송 무관 코어, 페어링, 라우팅, 리댁션, 청킹, 마크다운, 다이제스트, 브리지, pi 어댑터 셸 | 186 테스트 통과, typecheck 통과, Telegram 없이 전 구간 검증 |
| **v1** | Telegram 어댑터(롱폴링) + 단일 인스턴스 락 + 로컬 명령 완성 | 실제 봇으로 왕복 1회, 터미널 복귀 시 맥락 유지 확인 |
| **v2** | 핸드오프 명시화(`handoff`), 진행 상황 편집(edit-in-place), Discord 어댑터 | 두 전송이 같은 conformance 테스트 통과 |
| **v3** | Slack, 어댑터 conformance 키트 공개, 리플레이 하네스 | 외부 기여 어댑터 1개 |

### v0에서 이미 확정된 것 (테스트로 고정)

- 페어링 코드는 **로컬 터미널에만** 표시된다 (`src/core/pairing.test.ts`)
- 프롬프트 본문은 **로그에 남지 않는다** (`src/bridge.test.ts`)
- 송신 본문은 **리댁션을 거친다** (`src/core/redact.test.ts`, `src/bridge.test.ts`)
- 청킹은 UTF-8 경계를 깨지 않는다 (`src/core/chunk.test.ts`)
- 전송별 마크다운/길이 제약이 코어에서 처리된다 (`src/core/markdown.test.ts`)
- 설정 파일은 **비밀값을 담을 수 없다** (env 변수 이름만) (`src/config.test.ts`)
